# Receiving Core handoff audit — October 25, 2026

The [supplied handoff](unity-receiving-cores-approved-handoff.md) is preserved
verbatim. Its approved decisions are design authority; proposals and open
decisions are not silently promoted into authored gameplay.

| Status | Finding |
| --- | --- |
| Compatible foundations | Physical rooms retain their own Core capacities; ordered Groups preserve child identity. Shared room/schema imports, persistent physical cargo, Warehouse capacity and the universal bubble executor are reusable. |
| Partial / conflicting | Receiving currently has an effective static processing capability and Balanced defaults, rather than embedded T0 plus owned installed Medium/Balanced Cores. Current Large cache processing is not gated by handling equipment; it would exceed the approved starter Medium Core. |
| Approved, not implemented | Embedded T0 outside removable slots; cumulative handling equipment; distinct recovery Cores; cargo-authored preference hierarchy; compatible emergent Services; permitted redundancy; degradation separate from binary Services; Generator100 PWR and active-capacity reservation; queued reconfiguration. |
| Missing authoring | Starter canonical Core/Service IDs and complete definitions, installation/removal Recipes and inputs, per-Core Idle/Active costs, room base PWR, numerical T0 recovery, compatibility tags/hierarchy and legacy instance seeding. Shared theory data currently has the two electrodynamics technical Core definitions, not the starter Receiving equipment. |
| Storage boundary | Installed Cores specifically release Warehouse places under the handoff. Ordinary physical items retain validated fallback reservations. Core custody must implement that explicit lifecycle rather than reusing ordinary storage reservations unchanged. |
| Reversibility boundary | Installation/removal is reversible custody/configuration work. It is distinct from physical construction cancellation/salvage; irreversible consumables still need explicit Recipe semantics. |

No physical starter Core, free Service, power cost, acquisition path or
installation timing has been invented for the Wave2 build. The current
Balanced playtest default remains explicit until Wave3 is authored.

The smallest next authoring package is: starter Medium/Balanced definitions and
their IDs, room/Core PWR values, the reversible installation Recipe, T0 recovery
numbers and migration seeding. It must also resolve how the Large reference
cache is processed with the approved Medium starter equipment. Higher-tier
recovery distributions, fuel, disruptions and broad damage/repair remain deferred.


## October 25 follow-up: authorized first pass

The user subsequently authorized Medium cache sizing and provisional Recipes /
power costs. [First-pass authoring](unity-receiving-cores-first-pass.md) records
the shared sources and values. Six Receiving Cores, reversible installation,
physical item definitions, starter IDs, room/Core PWR, T0 recovery and capability
preferences are now authored and projected. The Medium cache/save transition is
implemented; Core ownership, installation, Service selection and PWR enforcement
remain Wave3 runtime work. The missing-authoring / Large-conflict rows above
record the original handoff audit and are superseded for those specific gaps.
